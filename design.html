Back office blocks

Every block on this page is rendered by the real styles.css, with the real class names. If something looks wrong here it is wrong in the product, and fixing it here is fixing it there. Nothing on this page is a mockup.

How to use this

Building a screen: find the block, copy the markup under it, fill it with your data. Do not write new CSS for a screen. If no block fits, add one here first — as a new numbered block at the bottom of styles.css — then use it.

  • CSS lives in numbered blocks at the end of styles.css. Last block wins, so edit the newest one that owns the thing, never an older one — the change won't paint.
  • Current head: ROW BLOCKS (v32). Tokens are in SHOPIFY ADMIN REDESIGN (v21).
  • Bump ?v=NN on styles.css and backoffice.js in backoffice.html (and on this page's link) whenever you ship.
  • Every colour, size, radius and gap comes from a --po-* token. Typing 8px or #E1E1E1 means the token already exists and you missed it.

The five rules

  1. One card, one surface. A card is a single white box with a hairline. No box inside a box — head, body and table all sit on the same white.
  2. Separate with a hairline or a stripe, never with a second surface — and never with both at once.
  3. A row is one line of text. A second fact goes beside the name, never under it. If a cell needs two lines it is the wrong cell.
  4. Money and counts are tabular and right-aligned. Labels are sentence case, tertiary ink, never caps.
  5. Depth comes from hairlines, not shadows. Only a genuinely floating layer (a menu, a toast) casts a shadow.

Type

One typeface: Geist. A second face on the same screen reads as a second design. What makes a column of money line up is font-variant-numeric: tabular-nums, not a monospace font — add .num and let the token do it.

Row text and table text are sized by --po-row-font, which Settings → Appearance moves between 12 / 13 / 15px. Nothing in a row may carry a hardcoded font-size or height — derive from --po-row-font and --po-row-h or it breaks at S and L.

Space & radius

  • 14px is the card's left edge. Head, body, every row and every table cell line up on it. A child that doesn't respect it visibly steps in or out.
  • 10px between cards (--po-gap). 12px inside a grid of stats, 16px inside a settings form. Reach for an existing step — no one-off 13px or 21px.
  • 8px radius on everything (--po-r-card / --po-r-button / --po-r-input). Small nested things sit at 6px, pills at 999px. No 12px, no 16px.
  • One row height (--po-row-h, 32px at M). A row of text, a row with a pill and a row with a button all measure the same; a control inside a row is calc(var(--po-row-h) - 8px).

Card

The container everything else goes in. Three levels, never a fourth, and never a .bo-card inside a .bo-card. Two regions in one card are two .bo-card-inset children — the hairline between them comes free.

Card title a fact, right
Body text sits on the card's own white. There is no inner box, no second border and no second grey — .bo-card-inset is padding and nothing else.
A second inset is a second section of the same card. The hairline above it is automatic.
  • A link or a count in the head, right — .bo-card-sub or .link-btn. Never under the last row: a link below a list reads as one more row.
  • Table or chart inside? Add .flush and let it bleed to the card edge.
  • No border-bottom on the head. Where a table follows, its tinted header strip is the boundary.

Table

Once a row needs more than a label and a value, it is a table. Dense: one line per row, 6px 14px in a cell, nothing wraps — a long SKU scrolls sideways inside .table-wrap rather than doubling every row’s height. Striped by default (v33): the band is what your eye rides across a wide row, and it is why the hairline is gone — stripes or rules, never both.

Buttons

Three variants, three heights, one class. Anything outside this set is a one-off, and a one-off is what nobody remembers to restyle when the palette moves. The geometry is shadcn’s (rounded-md, 13px medium, 6px icon gap); the colours stay ours.

Manage inventory →
  • One primary per screen — the thing you came to do. Everything else is default or ghost.
  • .btn.danger is for the confirm inside a dialog, never sitting in a toolbar next to Save. In a toolbar a destructive verb is a quiet link, pushed left.
  • Heights are 26 / 32 / 38. The 32 is the default and matches an input, so a button beside a field lines up without anyone having to think about it.

Popup menu

Built on the browser’s own popover attribute — no library and no JavaScript at all. The browser gives us the top layer, click-outside to dismiss, Esc, and focus return: every part a hand-rolled dropdown gets wrong. Open it, then press Esc.

  • The motion is shadcn’s: fade plus a 96% zoom, 150ms in, 100ms out. A panel that lingers on the way out feels broken; one that eases in feels considered.
  • It animates both ways because of @starting-style and transition-behavior: allow-discrete. Without those two you can fade a menu in but it vanishes on close — that snap is the tell of a cheap menu, and it is exactly what ours used to do.
  • Never more than about seven items. Past that it is a page, not a menu.

Dialog

The same motion with a backdrop that fades alongside it. Native <dialog>, so Esc, the focus trap and the scroll lock are the browser’s problem and not ours.

The sale stays in the ledger as a voided row and the stock goes back. This cannot be undone.
  • The title is a question, the body says what will happen, and the confirm button is the verb — “Void sale”, never “OK”. Someone clicking fast should still be able to read the button and know what they just did.
  • Cancel sits on the left and is the plain button. The dangerous one is never where your hand lands by default.
  • A dialog is for a decision. Anything you have to fill in is a page.

Focus & states

Tab through this. One ring for the whole product: a 3px translucent halo in the accent plus a solid border. It reads on any background and never shifts layout, which is why it replaced the four different focus styles that had piled up.

And a link
  • Never outline: none without putting a ring back. Half of this app is driven from a keyboard at a counter.
  • :focus-visible, not :focus — a mouse click should not light a button up.
  • Row hover is a darkening layer (rgba(0,0,0,.045)), not a grey. It has to show on a striped row as well as a white one, and a flat grey vanishes on the stripe.

The rest

  • A card inside a card. Two borders, two radii and two greys for one card's worth of content. A hairline tells things apart.
  • A heavy shadow, or a 0 0 0 1px ring on top of the border. It doubles the hairline and the card starts to float.
  • A big number alone in a tall cell. ₱0 at 25px in 100px of white is what made Overview look broken on an empty day. The stat row sizes to its text.
  • A row of separate stat boxes across the page. Six numbers, six cards, and the sales below the fold.
  • ALL CAPS labels and letter-spacing. Sentence case, plain, tertiary.
  • A second typeface for numbers. tabular-nums does the aligning; a mono face just reads as a second design.
  • A link under the last row of a list. Put it in the card head.
  • A hardcoded height or font-size inside a row. It looks right at M and breaks at S and L.
  • A blue that isn't a link. --po-accent-link is for links, full stop.

What we borrow

We do not adopt anyone's design system — a component library is a build step and this app has none. What we take is the decisions: the row rhythm, the token names, the rules about when a thing is a card. Verified 2026-09-20.

shadcn/ui — the geometry and the interaction

ui.shadcn.com. MIT, no field-of-use clause, and unusually it is not a dependency even for the people who use it properly — it hands you the source and you own it. That is the licence we want and the philosophy we already had.

We do not run npx shadcn init, because that scaffolds React and Tailwind and this app has neither. What we did instead is read its registry directly (ui.shadcn.com/r/styles/new-york-v4/*.json, which is just the component source as JSON) and port the recipes into plain CSS. What came across:

  • The focus ring — 3px translucent halo plus a solid border, on :focus-visible. Their best single idea; it replaced four different focus styles here.
  • The popup motion — fade plus 96% zoom, 150ms in, 100ms out. The part you liked. Ours does it on the native popover attribute with zero JS, which they cannot do because they are on Radix.
  • The button set — variants and heights, rounded-md, 13px medium, 6px icon gap.
  • The radius ladder — sm/md/lg/xl, sized onto our existing 8px card instead of their 10px base.

What did not come across: their palette, their density and their table. Their neutral is a cold grey and ours is warmer; their header row is h-10, which is a web app's, not a till's; and their table has no stripes at all, which we tried and rejected — the zebra stays. That mix is the blend. A page built from these blocks should not be mistakable for a shadcn demo or for Shopify admin.

Shopify Polaris — the reference, with a catch

shopify.dev/docs/api/polaris (polaris.shopify.com now redirects here). Read the licence before copying anything.

  • @shopify/polaris-tokens is plain MIT — the numbers are free to take. That is the package to read.
  • @shopify/polaris (the React components) and polaris-viz are MIT plus a field-of-use clause: the rights only cover apps that are "dissimilar and visually distinct from Shopify products". Taking their values is fine. Lifting their component CSS into a non-Shopify product is not, and we don't.
  • Polaris React has been frozen since March 2025 and the repos are archived. Its replacement, Polaris Web Components / Polaris 2.0, publishes no token file and its components explicitly cannot be styled with custom CSS — so there is nothing newer to borrow.
  • Shopify shipped a new admin look on 2026-09-15. The values below are the admin before that refresh. They are still the only published, machine-readable Polaris numbers.

The one worth arguing about: polaris-viz paints a falling number in neutral grey with a down arrow, and keeps red for errors and destructive actions. Ours goes red, which is why a quiet day with no sales renders as ₱0 next to a red ↓100% — the card looks like an incident, not a slow morning. Direction and sentiment are also separate there: refunds rising is an up arrow that is bad news. Not changed yet.

The others

  • IBM Carbon — carbondesignsystem.com, Apache-2.0, actively maintained, tokens published as W3C DTCG JSON. The best free writing on data tables and density — it ships four row heights the way we ship three. Its look is not ours; take the reasoning.
  • GitHub Primer — primer.style, MIT, the richest downloadable token set of any of them. Worth reading for dense tables and for its do/don't format.
  • Adobe Spectrum — Apache-2.0, tokens as schema'd JSON. Strongly branded; reasoning only.
  • Atlassian — the npm package says Apache-2.0 but the system's own licence limits it to software that integrates with Atlassian products. Same trap as Polaris React. Read, don't adopt.
  • The actual POS competitors have nothing public. Square's admin system (Market) is internal — the public @square/maker is a different, Vue thing. Lightspeed's token package was abandoned in 2019. Toast and Intuit publish no design system at all. They are only useful as screenshots.

The rule when borrowing: a decision comes in as a sentence — here or in docs/backoffice.md — first, then as CSS in a new numbered block. Nothing arrives as a copied stylesheet, and no dependency is added. The product has no build step and is not getting one.
